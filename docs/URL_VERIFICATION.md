# Production URL verification

The interactive `message_type="link"` path uses policy `url-staged-v6`. See
[the reliability follow-up](URL_RELIABILITY_FOLLOWUP.md) for the current risk-memory,
isolated VT detection, optional Google reputation, and cache-expiry contract.
The v6 SPA fallback is opt-in and **not production acceptance passed**. See the
deployment and live-test limitations at the end of that follow-up.

The opt-in [local isolated renderer worker](LOCAL_RENDERER_WORKER.md) is a
separate credential-free container prototype. It uses the same page-evidence
and staged verdict pipeline; it has not been activated on deployed hosts.

1. Normalize HTTP(S), validate public DNS/SSRF, follow bounded HTTP/meta redirects, and fetch at most 1 MiB of each response. One HTTP client is shared within the request; the final response stream is reused without a duplicate page fetch. Redirect headers/DNS/transitions share a three-second budget, while all body reads share a separate two-second budget inside the combined five-second resolver and nine-second global deadline. This allows a long script-heavy head without treating metadata alone as benign evidence.
2. Extract lightweight page evidence and check local blocklist/URL heuristics. Only after these core checks finish does routing select optional providers.
3. A trusted final origin with sufficient clean core evidence takes `FAST_SAFE`: Gemini and VirusTotal are both `skipped_not_needed`.
4. An unknown origin with sufficient clean core evidence takes `AI_CONFIRMATION`: Gemini runs first. An explicit high-confidence clean assessment skips VirusTotal.
5. Uncertain Gemini or insufficient core may request VirusTotal afterward. Deterministic suspicious evidence can request VT without Gemini; provider failure cannot erase that risk. Malicious evidence returns immediately without waiting for optional providers.

No Gemini or VT task starts speculatively in parallel. Every invoked stage is bounded by `min(configured_timeout, global_deadline - elapsed)`.

## Trusted-origin and benign-evidence policy

`URL_TRUSTED_ORIGINS` is a comma-separated list of exact HTTPS origins without paths, query strings, fragments, or wildcards. Defaults are `https://www.youtube.com`, `https://youtube.com`, `https://www.wikipedia.org`, `https://en.wikipedia.org`, and `https://th.wikipedia.org`. Subdomains, HTTP, and different ports do not inherit trust. These are reviewed policy entries, not URL-specific return-safe branches. The rule always evaluates the validated final origin, including after shortener/meta redirects.

Trust alone never establishes a benign verdict. Core must include successful redirect resolution, readable non-interstitial page evidence (at least 80 visible text characters, not just a title or HTTP 200), no deterministic risk, and a successful local reputation/heuristic check. CAPTCHA, consent, JavaScript shells, empty bodies, and unavailable blocklist lookups are insufficient. A blacklist miss is `not_listed`, not positive clean reputation. Sufficient bounded content plus a reviewed trusted origin provides the fast-path benign evidence.

Unknown origins need Gemini to return a validated `assessment=clean`, `evidence_sufficient=true`, a nonempty evidence explanation, `category=SAFE_NORMAL`, and confidence at least 80/100. Confidence alone is insufficient and is never displayed as a percentage of safety. Explicit uncertainty, malformed schema, timeout, or low confidence cannot establish benign evidence. A clean VT result alone cannot compensate for unreadable/insufficient core or uncertain Gemini.

## Verdicts

- `MALICIOUS`: malicious evidence after source interpretation (a lone VT malicious engine is a suspicious warning under v5, not confirmation).
- `SUSPICIOUS`: no malicious evidence exists, but at least one source supplied suspicious evidence.
- `NO_THREAT_FOUND`: all required core checks passed and the selected route established high-confidence benign evidence. This does not claim absolute safety.
- `INCOMPLETE`: no malicious/suspicious evidence exists, but required core or benign-confirmation evidence is missing. Incomplete is never safe.
- `INVALID`: the URL is malformed, unsupported, resolves to a prohibited destination, or violates redirect safety limits.

The legacy fields (`category`, `risk_level`, `is_fraud`, `is_safe`, and `url_check`) remain present. `is_safe` is `true` only for `NO_THREAT_FOUND`; it is `null` for `INCOMPLETE` and `INVALID`.

Each check has `required` and `complete`. `skipped_not_needed` has `required=false` and `complete=null`: it is neither clean evidence nor a failure. VT is optional corroboration, so its timeout cannot downgrade established `SUSPICIOUS`/`MALICIOUS` evidence. `verification_complete` records whether required checks completed; a danger verdict may still have incomplete core checks. Completed evidence and the resolved final URL survive the global deadline. `verification_route`, `policy_version`, route reasons, per-stage elapsed time, explicit skips, and final verdict appear in structured logs without page bodies or URL query strings.

Every URL result displays a Thai verification explanation. Completed Thai Gemini explanations consistent with the aggregate verdict are attributed to AI; other results use a deterministic Thai summary of the reported evidence/verdict. A validated fast path explains why AI was not needed, and truncated content is described as a bounded preview rather than the whole page. English explanations in existing cached/provider responses receive the Thai system summary, not an invented translation or an extra provider request. The URL prompt explicitly requests Thai `reason_th` for future Gemini responses. This display behavior does not change routing, verdicts, cache data, provider counts, or deadlines; legacy text results retain their existing presentation.

## Security and latency boundaries

User-entered bare hostnames (for example `example.com` or `example.com/path?q=1#part`) default to HTTPS at the URL-verification entry point. Explicit HTTP/HTTPS URLs retain their scheme; unsupported schemes are never rewritten. The normalized URL drives the same public-DNS, redirect, content and provider pipeline and cache key as an explicitly entered HTTPS URL. History retains the original user input. Redirect target validation and trusted-origin policy parsing still require explicit HTTP(S); this input convenience does not relax their safety boundary or automatically retry HTTP when HTTPS fails.

Only HTTP and HTTPS are accepted. Every hostname is resolved before connection, and any loopback, private, carrier-grade, link-local, multicast, reserved, unspecified, or otherwise non-global address blocks the request. HTTP redirects and conservatively parsed HTML meta refreshes of at most five seconds are followed manually with one shared five-hop cap and three-second transition budget; relative locations, loops, and public-to-private redirects are handled explicitly. Body reads share a separate content budget across all meta hops, are not charged twice against the transition budget, and cannot reset the header deadline. Finding a meta redirect after the transition budget is exhausted cannot start another hop. The lightweight path does not execute JavaScript; the optional v6 renderer described in the follow-up may assess insufficient HTTP 2xx SPA evidence on an isolated sandbox-capable host. Metadata records whether the bounded HTML preview contained no supported client redirect or could not be parsed safely. TLS verification remains enabled. Response content is streamed and capped at 1 MiB per response for interactive inspection.

The page analyzer extracts bounded title, description, visible text, form/action, password/OTP, bank/authority impersonation, urgent-payment, and gambling signals. Script, style, template, and raw HTML are excluded. Gemini uses a dedicated URL/page prompt that labels the extracted webpage text as untrusted evidence and instructs the model to ignore instructions inside it; the ordinary user-message prompt is not reused. Only derived signals—not raw page text—are returned or cached. A page body that cannot be fetched or read makes content evidence incomplete rather than clean.

DNS validation and the HTTP connection are separate operations because the current HTTP client does not pin the validated address. This leaves a residual DNS-rebinding window between validation and connection. Production deployment therefore requires an outbound network policy that denies private, loopback, link-local, and metadata ranges even if DNS changes between validation and connection.

Configured budgets are 3 seconds for redirect transitions, 2 seconds for body reads (at most 5 seconds combined for resolution/fetch), 2.8 seconds for VirusTotal, 2 seconds for local/content analysis, 4.5 seconds for Gemini, 9 seconds overall, and 12 seconds in the frontend. The opt-in renderer receives up to 4 seconds with 1.8 seconds reserved for cleanup inside the remaining global budget. The remaining global time always takes precedence; these budgets are not added into a longer fixed request timeout. Timed-out streams are closed. A body timeout retains received danger signals but cannot establish clean core evidence. Redirect timeout responses preserve already discovered hops, which does not imply that a discovered destination was fetched or verified.

The Firestore local-reputation lookup has a dedicated 1.0-second RPC timeout and disables retries. Risk-history reads also have a dedicated 1.0-second native timeout inside a 1.2-second stage cap, with no retries; risk writes and other database operations retain their 0.5-second RPC budget. The global URL deadline remains nine seconds. `local_reputation_lookup` logs stage, outcome, configured timeout, elapsed milliseconds, and—on failure—exception class and a numeric/enum status code. Risk-history failures preserve sanitized timeout/error type and elapsed metadata. Neither diagnostic logs the exception message, document data, URL, credentials, or headers. These diagnostics do not change verdict semantics or turn unavailable reputation into clean evidence.

Legacy prescreening in `/check-fraud` text mode and the LINE webhook now performs local pattern analysis only. Its previous short-link/headless network enrichment did not enforce the SSRF boundary and is intentionally disabled; URL-mode checks use the bounded verifier, while text-mode URL reputation remains best-effort without headless browsing.

## VirusTotal and caching

VirusTotal is best-effort evidence. Its statuses are `clean`, `malicious`, `suspicious`, `not_found`, `pending`, `rate_limited`, `timeout`, `unavailable`, and `error`. Only a completed analysis with zero malicious and suspicious detections is `clean`. Unknown URLs are not uploaded by default (`VIRUSTOTAL_SUBMIT_UNKNOWN_URLS=false`); enabling submission has privacy and quota implications, and a new submission remains `pending`.

Completed VirusTotal evidence is normalized and cached locally. `not_found` remains incomplete but is cached in-process for 30 minutes to avoid repeatedly spending the free public quota on the same normalized URL. Pending, timeout, unavailable, error, and rate-limited results are not cached. In-flight duplicate lookups share one request. Local guards enforce the configured free-tier minute/day budgets and a cooldown after HTTP 429 without retrying inside the interactive request.

Only complete, non-invalid aggregate URL results enter the persistent cache. Benign results have a maximum one-day lifetime; risk results have a maximum fifteen-minute lifetime, and provider expiry can shorten either. Inherited risk does not enter the aggregate cache. Incomplete core/confirmation results are not cached, but newly completed positive evidence is saved separately. Optional VT failure does not erase a suspicious verdict. Cache keys include `url-staged-v6` and a digest of trusted-origin, external-reputation and renderer opt-in policy. Earlier pipeline entries and entries without matching policy/verdict/completeness metadata are ignored. Checks, route, required/skipped metadata, and resolved URLs remain in cached results/history.

## Validation boundaries

`tests/test_url_staged_routing.py` covers acceptance A-I using the actual verifier/resolver with deterministic mocked public DNS, bounded HTML transport, Gemini, VT, and cache misses. It asserts provider await counts and ordering, redirects out of trust, lookalikes, insufficient core, optional-provider failure, early malicious results, deadline cancellation, and preserved evidence. This proves routing behavior, not the availability or accuracy of live providers or current HTML served by YouTube. Live regressions must report their actual content sufficiency and timing; an unreadable live page remains incomplete under the same policy.

An earlier v3 regression on 2026-10-01 used real DNS/HTTP but mocked local reputation and disabled real Gemini/VT requests: the 64 KiB limit ended inside YouTube's script-heavy head, so it correctly remained incomplete. After the bounded v4 fetch change, one authorized fresh attempt per URL used real DNS/HTTP/local reputation and enabled the actual Gemini/VT functions according to routing (unknown VT URL submission was disabled):

- YouTube: `NO_THREAT_FOUND` / `FAST_SAFE` in 1.344 seconds; complete 898,999-byte response, 177 visible-text characters, no deterministic risk, local `not_listed`; Gemini invocations = 0 and VT invocations = 0. No URL-specific branch or weakened evidence threshold was used.
- qr1.be/ET2MJ2: `INCOMPLETE` / `CORE_FAILURE` in 2.188 seconds; the redirect chain discovered `https://www.nectapharma.com/`, but the transition deadline expired before destination verification completed. Discovered URL is not a verified final destination. Gemini invocations = 0 and VT invocations = 0 because redirect/core could not complete.

Neither URL was retried in this follow-up. These results prove the live YouTube fast path and bounded incomplete behavior, not live Gemini/VT connectivity: neither provider was needed/invoked. Their escalation/order/error semantics remain covered by deterministic tests. Current live webpages, provider availability, and latency can change; title, trusted origin, or HTTP 200 must never override insufficient page evidence.

The pre-adjustment Python-documentation regression on 2026-10-01 ran the real verifier once without aggregate cache, provider mocks, cache/history writes, or a retry of the test. The page and redirect checks completed cleanly (19,596 response bytes; 4,096 bounded visible-text characters; no deterministic signals). The new local lookup diagnostic recorded `DeadlineExceeded`, status code 504, after 531 ms with the then-current 0.5-second Firestore RPC timeout. This code belongs to the Firestore exception, not a Render/proxy HTTP response. Gemini returned clean (one pipeline invocation), then optional VT returned clean (one pipeline invocation); the missing required local check correctly kept the overall result `INCOMPLETE` / `CORE_FAILURE`, in 3.313 seconds. The four-part acceptance gate was **NOT PASS** for that fresh run. Provider invocation counters do not count SDK-internal HTTP retries. The live test was not repeated in that round and neither timeout nor verdict policy was changed then. This confirmed a lookup deadline failure in that run, but did not establish whether cold connection setup or transient network latency caused it.

After the separately authorized local lookup budget adjustment to 1.0 second, one fresh native regression of `https://docs.python.org/3/tutorial/appetite.html` on 2026-10-01 passed all four acceptance assertions in 2.313 seconds: required core completed with 19,596 response bytes, 4,096 visible-text characters, and no suspicious signals; local reputation completed as `not_listed` in 484 ms; real Gemini returned clearly clean with sufficient evidence (one pipeline invocation); VirusTotal was `skipped_not_needed` (zero invocations). The result was `NO_THREAT_FOUND`, `verification_complete=true`, route `AI_CONFIRMATION`, policy `url-staged-v4`. This direct verifier run bypassed aggregate cache and performed no cache/history writes or unknown-URL submissions. No provider was mocked and the live test was not retried. The counters measure pipeline invocations, not SDK-internal HTTP attempts. This is a successful local native acceptance observation, not a production deployment or a guarantee of future provider latency; the one-second budget is still bounded and later failures remain incomplete rather than safe.

One separately authorized native VirusTotal-only lookup on 2026-10-01 used `https://www.amtso.org/check-desktop-phishing-page/` with a fresh service and unknown submissions disabled. Real HTTP client request/response hooks recorded exactly one GET, zero POSTs, and HTTP 200 within 0.844 seconds under the 2.8-second total deadline. The uncached completed provider evidence was `malicious` (12 malicious, zero suspicious, 92 total engines). No Gemini call, persistent cache/history write, repeated attempt, or leftover in-flight task occurred. This proves live VT connectivity and native malicious-evidence parsing, not end-to-end escalation: earlier AMTSO aggregate results legitimately skipped VT after clean core/Gemini under the selected policy. AMTSO describes this URL as a harmless anti-phishing test indicator, so provider classification here is not independent proof of actual phishing content. If the staged verifier invokes VT and receives malicious evidence, deterministic aggregation must return `MALICIOUS`; automated routing/aggregation tests cover that separate behavior. No URL-specific production exception or forced provider call was added.
